# Repository Guide

## Overview

SSML-Builder is a TypeScript monorepo for generating and parsing Azure Speech SSML, editing it with a React component, and synthesizing audio through Azure Text-to-Speech. It uses npm workspaces for both `packages/*` and `apps/*`.

## Repository Layout

- `packages/ssml-core`: Core SSML types, document building, partial SSML generation, parsing, and validation.
- `packages/ssml-editor-react`: React SSML editor built with Monaco Editor. `src/SsmlEditor.tsx` contains the component, insertion definitions, and public props/ref types.
- `packages/azure-tts-client`: Microsoft Speech SDK client for Azure Text-to-Speech. It exports both `AzureTtsClient` and the lower-level `synthesizeSpeech` function.
- `packages/*/src/index.ts` and `packages/ssml-editor-react/src/index.tsx`: Public package entry points.
- `packages/*/test`: Node.js built-in test-runner tests for the packages.
- `apps/playground/app/page.tsx`: Client-side playground UI for editing SSML, selecting a voice, and generating audio.
- `apps/playground/app/api/synthesize/route.ts`: Node.js Route Handler that validates request JSON and SSML before calling Azure TTS; Azure credentials remain server-side.
- `apps/playground/.env.example`: Example server-side Azure Speech configuration.
- `biome.json`: Repository-wide Biome formatter and linter configuration.
- `.github/workflows/ci.yml`: CI jobs for formatting, linting, and package tests.
- `.github/workflows/release.yml` and `.changeset/config.json`: Changesets-based release automation for pushes to `main`.
- `packages/*/dist` and `apps/playground/.next`: Generated output; do not edit or commit it.

## Setup and Commands

Use Node.js 24 or later, matching CI. From the repository root:

```sh
npm ci
```

The root scripts delegate to workspaces when a workspace defines the requested script:

| Command | Purpose |
| --- | --- |
| `npm run format` | Check formatting with Biome |
| `npm run format:write` | Apply Biome formatting |
| `npm run lint` | Run Biome static checks |
| `npm run check` | Run Biome formatting and lint checks together |
| `npm run typecheck` | Type-check all workspaces that define the script |
| `npm run build` | Build all workspaces that define the script |
| `npm test` | Run tests in workspaces that define the script |
| `npm run dev --workspace playground` | Start the Next.js playground |
| `npm run start --workspace playground` | Start the built Next.js playground |
| `npm run changeset` | Create a Changeset for a publishable package change |
| `npm run version-packages` | Apply Changesets to package versions and changelogs |
| `npm run release` | Build and publish packages through Changesets; normally invoked by release automation |

Package tests use Node.js's built-in test runner with TypeScript strip-types support. The playground has a build and typecheck script but no test script. The current CI workflow runs `npm run format`, `npm run lint`, and `npm test`; run typechecking and builds locally when validating changes that affect them.

## Development Guidelines

- Keep package implementation in that package's `src` directory and export public APIs from its `src/index.ts` or `src/index.tsx` entry point. Package declarations are generated by each package's `tsup` configuration.
- Keep the core document `children` representation preferred; `SsmlDocument.content` is a deprecated compatibility input for `buildSsml`.
- Keep playground code under `apps/playground/app`; keep Azure credentials in the server-side route rather than browser code. The route returns client errors for invalid JSON or SSML before contacting Azure.
- Preserve the repository's strict TypeScript and ES module configuration. Do not weaken `strict` or introduce `any`; use `unknown` with a type guard when a value is not known at compile time.
- Use `import type` for type-only imports. Keep npm as the package manager; do not add yarn or pnpm workflow files or commands.
- Keep a final newline in every text file.
- Use Biome rather than Prettier. Follow `biome.json` and the existing style: two-space indentation, double-quoted strings, trailing commas, and a 120-character line width.
- Let Biome determine ordinary line wrapping. Keep short object literals on one line when readable, and use blank lines to separate logically related function groups.
- Prefer early returns for simple conditional results instead of deeply nested or unnecessarily clever ternaries.
- When a function call or callback becomes difficult to read, derive meaningful local values first and pass a named `params` object. Destructure input objects where useful and prefer shorthand properties. Extract complex `map`, `filter`, and `flatMap` callbacks into named functions.
- Keep React hooks focused: prefer one custom hook per file, and split a hook when it develops unrelated responsibilities. Use `useMemo` and `useCallback` only when they avoid a measured or clearly expensive recomputation, preserve referential identity needed by an effect/child, or are required for an imperative integration.
- Keep view files centered on a primary component. Extract substantial secondary components or complex logic when a file becomes difficult to navigate; do not split small render helpers mechanically.
- The playground intentionally uses the Next.js App Router under `apps/playground/app`; do not migrate it to the Pages Router.
- Keep dependencies and workspace references in each package's `package.json`; keep the root `package-lock.json` in sync with dependency changes.
- Do not commit `node_modules`, generated output, build caches, local environment files, or credentials. `.env.example` files may be committed.
- Supply Azure credentials at runtime through `AzureTtsClientOptions` or the playground's `AZURE_SPEECH_KEY`, `AZURE_SPEECH_REGION`, and optional `AZURE_SPEECH_ENDPOINT` environment variables. Never hard-code, expose to the browser, or log subscription keys or full SSML content.
- Keep the Japanese and English README API sections synchronized with the exported types and behavior, including `SsmlEditor` props/ref methods, insertion definitions, and the core/TTS overloads.
- When public package APIs change, update the relevant README documentation and include a Changeset when the release requires one.

### React and styling boundaries

- Define new component prop contracts with `interface` when they are component-specific and expected to be extended; preserve existing public type aliases when changing them would unnecessarily alter the API.
- Keep complex editor or playground logic in focused helpers or custom hooks rather than expanding the render path.
- This repository currently uses component-scoped inline style objects and does not include shadcn/ui, Radix UI, or Tailwind CSS. Follow the existing styling approach unless a future feature deliberately introduces a documented styling system.

### Out-of-scope technology rules

- There is currently no MongoDB integration. If MongoDB is introduced in the future, use the official native driver rather than Mongoose unless the repository's architecture is intentionally revised and documented.

## Pull Requests

Keep changes focused and include the validation commands that were run. For code changes, run the checks relevant to the affected workspaces; the CI workflow currently runs `npm run format`, `npm run lint`, and `npm test`. Do not edit generated output; regenerate it only to validate a build. Check the CI workflow when changing repository configuration or when diagnosing CI failures.
